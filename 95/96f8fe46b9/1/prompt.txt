## 2. What a provider must implement

**Definition entry point:** `definePlatform` in `/packages/core/src/platform/define.ts` (two overloads: *regular* mode and *fusor* mode).

**The contract type:** `PlatformDef` in `/packages/core/src/platform/types.ts:275`. Its doc comment states the minimum viable integration: `name`, `config`, `lifecycle`, `user`, `space`, `messages`, `send`.

Required fields:
- `config: z.ZodType&lt;object&gt;` — provider config schema (line 345)
- `lifecycle.createClient(ctx: CreateClientContext)` / optional `lifecycle.destroyClient` (line 361). `CreateClientContext` (line 245) carries `{ config, projectConfig, projectId, projectSecret, store }`.
- `user.resolve({ input: { userID }, client, config, store })` (line 487), optional `user.schema`
- `space.create(...)` (line 436), optional `space.get`, `space.schema`, `space.params`, `space.actions`
- `messages: EventProducer&lt;...&gt;` (line 408) — **inbound**
- `send({ space, content, client, config, store }) =&gt; Promise&lt;ProviderMessageRecord | undefined&gt;` (line 425) — **outbound**

Optional:
- `actions?` (line 335) — two tiers: framework-recognized **platform-wise actions** `getAvatar`, `getDisplayName`, `getMembers`, `getMessage` (`PlatformWiseActions`, types.ts:93; key set `PLATFORM_WISE_ACTION_KEYS` in `/packages/core/src/platform/build.ts`), plus free-form platform-specific actions. Undeclared platform-wise actions get a default that throws `UnsupportedError`.
- `events?` (line 359) — extra streams beyond `messages` (`messages` key is reserved); surfaced flat as `spectrum.&lt;event&gt;` and `platform.&lt;event&gt;`
- `message.schema` / `message.actions` (line 369)
- `static?` — properties copied onto the returned provider callable

Key supporting types (all in `/packages/core/src/platform/types.ts`):
- `ProviderMessageRecord` (line 190) — `{ id, content, direction?, sender?, space, timestamp? } &amp; Record&lt;string, unknown&gt;`; the shape both `messages` yields and `send` returns
- `ProviderUserRecord` (line 207)
- `EventProducer&lt;TPayload, TClient, TConfig&gt;` (line 147) — `(ctx: { client, config, projectConfig, store }) =&gt; AsyncIterable&lt;TPayload&gt;`
- `Platform&lt;Def&gt;`, `PlatformInstance&lt;Def&gt;`, `PlatformSpace&lt;Def&gt;`, `PlatformMessage&lt;Def&gt;`, `PlatformProviderConfig&lt;Def&gt;`, `PlatformRuntime`, `AnyPlatformDef` (line 502)

**Message flow:**
- *Inbound (regular mode)*: long-lived `messages` async-iterable yields `ProviderMessageRecord`s → core's `wrapProviderMessage`/`buildMessage` in `/packages/core/src/platform/build.ts` inflates them into `Message` + `PlatformSpace` → fanned out on `spectrum.messages`.
- *Inbound (fusor mode)*: `createClient` returns `fusor(platformId, verify)` (a branded `FusorClient`). Inbound arrives as a protobuf `RawInboundEvent` over a WebSocket (`/packages/core/src/fusor/websocket.ts`, default `wss://fusor-ws.spectrum.photon.codes/v1/subscribe`) or via `spectrum.webhook()`. `verify(req: FusorVerifyRequest)` authenticates + parses; `messages: FusorMessages&lt;TPayload, TConfig&gt;` runs once per payload and returns record(s) / `fusorEvent(channel, data)`, and may call `respond(reply)` to shape the HTTP reply. Types in `/packages/core/src/fusor/types.ts`; routing in `/packages/core/src/fusor/core.ts` (`RegisteredFusorHandler`).
- *Outbound*: everything (text, reaction, reply, typing, edit, rename, avatar, unsend, poll…) funnels through the single `send` switch on `content.type`. Sugar like `message.reply()`, `space.startTyping()` is built in `build.ts` and routes to `send`.

**Lifecycle hooks:** only `lifecycle.createClient` (required) and `lifecycle.destroyClient` (optional). Platform ID must match `/^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$/` — enforced by `assertValidPlatformId` (define.ts:40), so use `sim_ai`, not `sim.ai` or `simAI`.

## 4. Registration &amp; discovery

There is **no runtime plugin registry** — registration is explicit and type-driven:

1. `provider.config(cfg)` returns a `PlatformProviderConfig` tagged object (define.ts:583) carrying `__name`, `config`, `__definition`.
2. Users pass them to `Spectrum({ providers: [...] })`. Options validated by `spectrumConfigSchema` in `/packages/core/src/spectrum.ts:175`; factory options interface `SpectrumFactoryOptions` at line 262 (`providers`, `options`, `telemetry`, `webhookSecret`), `SpectrumOptions` at line 141.
3. Core keys runtimes by platform id in `spectrum.__internal.platforms` (a Map); narrowing does `spectrum.__internal.platforms.get(platformId)` (define.ts:537).

Config declaration convention: a per-provider zod schema, usually in `src/config.ts` (`/packages/telegram/src/config.ts` → `configSchema`) or `src/types.ts` (`/packages/whatsapp-business/src/types.ts:19` → `z.union([directConfig, cloudConfig])` with an `isCloudConfig` discriminator; `/packages/slack/src/types.ts` likewise).

Env fallback is automatic: `definePlatform` wraps every config schema with `envAwareConfig(platformId, def.config)` (define.ts:525), implemented in `/packages/core/src/utils/env.ts` — every string-leaf field falls back to `SPECTRUM_&lt;PLATFORM&gt;_&lt;KEY&gt;` (e.g. `SPECTRUM_SIM_AI_API_KEY`). Helpers `envFor`, `fromEnv`, `toEnvKey`, `normalizePlatformName` are re-exported from `@spectrum-ts/core/authoring`.

Discovery surfaces you'd need to touch for a new provider:
- `/packages/core/src/utils/provider-packages.ts` — `OFFICIAL_PROVIDER_PACKAGES` map (id → npm name) powering `officialProviderInstallHint` diagnostics
- `package.json#spectrum` field: `{ key, import, label }` (see `/packages/telegram/package.json`)
- `/packages/spectrum-ts/scripts/generate-manifest.ts` — builds `dist/manifest.json` by scanning `packages/*/package.json#spectrum` and **validating against source** with regex `^export\s+const\s+(\w+)\s*=\s*definePlatform\(...` in `src/index.ts`; consumed by external scaffolders like `create-spectrum-app`. `label` must equal the `definePlatform` id, `import` must equal the exported const name.
- `/packages/spectrum-ts/src/providers/index.ts` (aggregate re-export), `/packages/spectrum-ts/src/providers/&lt;name&gt;/index.ts` (per-provider `export *` shim), `/packages/spectrum-ts/tsdown.config.ts` (entry map), `/packages/spectrum-ts/package.json` (`dependencies` + `exports`)
- Release tooling auto-discovers: `/scripts/release/packages.ts#publishablePackages()` picks up any non-private `packages/*`.

No CLI or onboarding flow lives in this repo (`create-spectrum-app` is external and consumes the manifest).

# 2. Interfaces implemented

There is one interface, `PlatformDef`, defined in **`/Users/qwerzl/Documents/Projects/spectrum-ts/packages/core/src/platform/types.ts:275`**. It is consumed by `definePlatform` in **`packages/core/src/platform/define.ts:338`**, which has **two overloads**:

- **regular mode** — `lifecycle.createClient` returns an SDK client; `messages` is a long-lived `EventProducer` async-iterable.
- **fusor mode** — `createClient` returns `fusor(name, verify)` (a branded `FusorClient`); `messages` becomes a per-webhook handler typed `FusorMessages&lt;TPayload, TConfig&gt;` (`packages/core/src/fusor/types.ts:48`).

The overload is selected by whether `messages` is a *typed reference* (non-context-sensitive → fusor) or an inline arrow (deferred → regular). See the long comment at `define.ts:314-337`.

Required members (`PlatformDef`): `name`, `config`, `lifecycle.createClient`, `user.resolve`, `space.create`, `messages`, `send`.
Optional: `lifecycle.destroyClient`, `space.get`, `space.schema`, `space.params`, `space.actions`, `message.schema`, `message.actions`, `actions` (platform-wise + platform-specific), `events`, `static`.

Platform-wise action names are fixed by `PlatformWiseActions` (`platform/types.ts:93`) and the runtime set `PLATFORM_WISE_ACTION_KEYS` in `packages/core/src/platform/build.ts:105`: **`getMessage`, `getMembers`, `getAvatar`, `getDisplayName`**. Omitted ones auto-wire to a thrower (`UnsupportedError.action`).

## Schema + env fallback (automatic)

`definePlatform` wraps every config schema with `envAwareConfig(platformId, def.config)` (`define.ts:526`). `packages/core/src/utils/env.ts:143` rewrites **every string-leaf field** to fall back to `SPECTRUM_&lt;PLATFORM&gt;_&lt;UPPER_SNAKE_KEY&gt;`. Precedence: explicit value &gt; env var &gt; schema default/required. Empty-string env is treated as unset.

**Telegram** — `packages/telegram/src/config.ts:35`:
```ts
export const configSchema = z.object({
  botToken: z.string().regex(BOT_TOKEN_PATTERN, "botToken must be in the form '&lt;id&gt;:&lt;token&gt;'"),
  webhookSecret: z.string().regex(SECRET_TOKEN_PATTERN).optional(),
  baseUrl: z.url().default(DEFAULT_BASE_URL),
});
```
Env vars (auto-derived): `SPECTRUM_TELEGRAM_BOT_TOKEN`, `SPECTRUM_TELEGRAM_WEBHOOK_SECRET`, `SPECTRUM_TELEGRAM_BASE_URL`. Also reads `SPECTRUM_SUPER_WEBHOOK` (Fusor edge domain, default `spctrm.dev`) in `src/webhook.ts:19`.

**iMessage** — `packages/imessage/src/types.ts:25`:
```ts
export const configSchema = z.strictObject({
  clients: clientEntry.or(z.array(clientEntry)).optional(),   // { address, token, phone }
});
```
Nearly empty by design: cloud mode takes credentials from `Spectrum({ projectId, projectSecret })`, not from the provider config. Extra env: `SPECTRUM_IMESSAGE_ADDRESS` (`auth.ts:214`), plus core-level `SPECTRUM_FUSOR_WS_URL` / `SPECTRUM_WEBHOOK_SECRET`.

# 4. Inbound flow

## Telegram (webhook, via Fusor)

1. **Registration** — `createClient` calls `ensureWebhook` (`src/webhook.ts:39`), which is idempotent: `getWebhookInfo` → only `setWebhook` when the URL differs. Target URL is `https://{slug}.spctrm.dev/telegram`.
2. **Delivery** — Telegram POSTs to the Fusor edge, which forwards a protobuf `RawInboundEvent` (whose `rawRequest` is the original HTTP/1.1 wire bytes) over either the Fusor WebSocket (`packages/core/src/fusor/websocket.ts`, started lazily on first `spectrum.messages` read) or a direct `spectrum.webhook(request, handler)` call.
3. **Route + verify** — `FusorCore.processEvent` (`packages/core/src/fusor/core.ts:327`) looks handlers up by `event.platform`, parses the inner request via `parseHttpRequest`, then `runHandlerOnce` calls `handler.verify(parsedRequest)`:
   ```ts
   // packages/telegram/src/verify.ts:63
   export const verify = (config: TelegramConfig): FusorVerify&lt;TelegramPayload&gt; =&gt;
     (req: FusorVerifyRequest): TelegramPayload =&gt; {
       if (config.webhookSecret) verifySecret(req.headers, config.webhookSecret);
       return parseUpdate(new TextDecoder().decode(req.rawBody));
     };
   ```
   A throw → 400, no retry. Secret check is `timingSafeEqual` on `x-telegram-bot-api-secret-token`.
4. **Map** — `handleMessages` (`src/inbound/messages.ts:123`) returns one `ProviderMessageRecord | undefined`. Self-echo is dropped via `botIdFromToken`; captioned media becomes `asGroup([caption, media])`; reactions get a synthetic id `reaction:{chat}:{msg}:{date}:{actor}:{emoji}`.
5. **Dispatch** — `routeHandlerResult` (`fusor/core.ts:106`) sends the record to `handler.pushMessage` → the per-platform `AsyncQueue` created at `spectrum.ts:602` → `createProviderMessagesStream` (`spectrum.ts:451`) → `resolveRecordToMessages` (`spectrum.ts:392`) which calls `buildSpace` + `wrapProviderMessage(record, …, "inbound")`, optionally flattening `group` content into N messages → `broadcast(...)` → `for await (const [space, message] of app.messages)`.

## iMessage (long-lived gRPC streams)

`messages: ({ client, projectConfig }) =&gt; remoteMessages(client, projectConfig, getProfileSyncGate(client))` — `packages/imessage/src/remote/stream.ts:499`.

Per configured line it merges **three** resumable streams (`messageStream`, `pollStream`, `groupStream`, the last only in dedicated mode), each built with `resumableOrderedStream` from `@spectrum-ts/core/authoring`: `subscribeLive` + `fetchMissed(cursor)` catch-up + per-event cursor. The line set is dynamic, so `createStreamGroup` + `addLineObserver` add/remove lines when cloud token renewal reconciles them (`src/auth.ts:163`). Self-echo is suppressed by `isFromMe`/actor checks. Non-retryable mapping throws become empty skip items so the cursor advances (`skipUnmappable`, `stream.ts:94`). Downstream the records enter the exact same `resolveRecordToMessages` pipeline as Telegram.

# 5. Outbound flow

## Telegram

`send` (`src/outbound/send.ts:158`) builds a fresh client per call (`telegramClient(config)` — cheap, no network), then:
```ts
const sendContent = async (client, space, content) =&gt; {
  const spec = await buildSend(content);
  const sent = await executeSpec(client, { ...spec, params: { chat_id: space.id, ...spec.params } });
  return { id: String(sent.message_id), content, space: { id: space.id }, timestamp: new Date(sent.date * 1000) };
};
```
- `buildSend` (`src/outbound/message.ts:88`) maps content → `{ method, params, file? }`: `sendMessage` / `sendPhoto` / `sendVideo` / `sendDocument` / `sendVoice`; `markdown` → `markdownToTelegramHtml` + `parse_mode: "HTML"`; `reply` recurses and adds `reply_parameters`; `custom` is an escape hatch to any Bot API method.
- **No text chunking anywhere in this repo** — neither provider splits long text.
- **Media out**: `executeSpec` (`src/client.ts:77`) posts JSON normally; with `spec.file` it wraps bytes in a `File`, uses a hand-rolled `toFormData` serializer and sets `Content-Type: null` so fetch computes the multipart boundary.
- **Media in**: `downloadFile` (`src/client.ts:108`) — `getFile` for the path, then one authenticated `fetch` through `tracedFetch("telegram", { redactUrl: redactBotToken })`. Attachments are lazy (`read: lazyRead(config, file.file_id)` in `src/inbound/media.ts`).
- `group` → N separate sends, last record returned. `reaction` → `setMessageReaction` with an allowlist pre-check, synthetic id returned. `typing` → `sendChatAction` (no "stop"). `read` → silent no-op. `streamText` → `sendMessageDraft` at 500 ms throttle, then a real `sendMessage` (`src/outbound/stream-text.ts`). Unsupported (`poll`, `effect`, `rename`, `avatar`, membership) throw `UnsupportedError.content`.

## iMessage

`send` (`src/index.ts:636`) routes by `content.type` to `clientForPhone(client, space.phone)` and the RPC wrappers in `src/remote/api.ts`. Every message-producing send passes through `cacheRemoteOutbound` (`index.ts:124`) which writes into the per-client LRU message cache — this is what lets inbound reactions/read-receipts resolve their targets. Guards: group-only for `rename`/`avatar`/`addMember`/`removeMember`/`leaveSpace`/`getMembers`/`getAvatar`/`getDisplayName` (`remoteGroupClient`, `index.ts:380`); polls reject `reply`/`react`/`unsend`. `streamText` sends the first chunk then edits it in place (`src/remote/stream-text.ts`). Attachments stream over gRPC in `primaryChunk` frames (`src/remote/attachments.ts`).

# 6. Registration — the exact places a new channel must be added

For an in-repo provider named `my_platform` in `packages/my-platform/`:

1. **`packages/my-platform/package.json`** — name `@spectrum-ts/my-platform`; `"type": "module"`; `exports` with the `bun`/`types`/`default` triple plus the `publishConfig.exports` override; `peerDependencies: { "@spectrum-ts/core": "^12.0.0", "typescript": "^5 || ^6.0.0" }`; devDeps `@spectrum-ts/core: workspace:*`, `@spectrum-ts/test-support: workspace:*`, `tsdown`, `vitest`; scripts `build` (`tsdown &amp;&amp; node ../../scripts/smoke-import.mjs dist/index.js`), `dev`, `test:bun`, `test:node`, `typecheck`; **and the manifest block**:
   ```json
   "spectrum": { "key": "my_platform", "import": "myPlatform", "label": "my_platform" }
   ```
2. **`packages/my-platform/src/index.ts`** — must literally match `/^export\s+const\s+(\w+)\s*=\s*definePlatform\(\s*(?:"([^"]+)"|(\w+))/m`, i.e. `export const myPlatform = definePlatform(MY_PLATFORM, {...})`. `generate-manifest.ts:70` validates that `import` === the exported const name and `label` === the platform id (resolving a shared const from any `src/*.ts` if not inline). Mismatch = build failure.
3. **`packages/my-platform/turbo.json`** — `{ "extends": ["//"], "tags": ["provider"] }`. The `provider` tag makes `turbo boundaries` forbid importing other providers.
4. **`tsconfig.json`** (`extends ../../tsconfig.json`, `include: ["src","test"]`, `paths: {"@/*": ["./src/*"]}`), **`tsdown.config.ts`**, **`vitest.config.ts`** (`spectrumTestConfig(import.meta.dirname)`), `LICENSE`, `README.md`.
5. **`packages/core/src/utils/provider-packages.ts:14`** — add `my_platform: "@spectrum-ts/my-platform"` to `OFFICIAL_PROVIDER_PACKAGES` so "no handler for platform" warnings emit an install hint.
6. **If batteries-included**: add to `packages/spectrum-ts/package.json` dependencies (pinned exact version), create the shim `packages/spectrum-ts/src/providers/my-platform/index.ts` (`export * from "@spectrum-ts/my-platform";` — a pure star export, deliberately), add a named re-export to `packages/spectrum-ts/src/providers/index.ts`, and add the pair to the `cases` array in `packages/spectrum-ts/test/providers-shims.test.ts`. (iMessage-local skips all of step 6 and has no `spectrum` field — see `packages/spectrum-ts/test/imessage-package-boundary.test.ts`.)
7. **Docs**: `docs/providers/my-platform.mdx.vel` + subpages, a card in `docs/providers.mdx.vel`, and a group entry in **`docs/nav.json`** under `"Providers"`.
8. **Nothing else.** Root `package.json` uses `workspaces: ["packages/*"]`, and `scripts/release/packages.ts` auto-discovers every non-private package under `packages/`.

Runtime registration is fully dynamic — `Spectrum()` iterates `providers` and stores `platformStates.set(def.name, …)` (`spectrum.ts:569`); fusor providers additionally self-register at `spectrum.ts:655` via `fusorCore.register(client.platform, handler)`. The `fusor(...)` key, the `definePlatform` name, and Fusor's URL path segment **must be the same string** — see the comment at `packages/telegram/src/config.ts:3-17`.

# Minimal template for a new HTTP/webhook channel

```ts
// packages/my-platform/src/config.ts
export const MY_PLATFORM = "my_platform";              // must match fusor key + Fusor path segment
export const configSchema = z.object({ apiKey: z.string(), webhookSecret: z.string().optional() });

// packages/my-platform/src/index.ts
export const myPlatform = definePlatform(MY_PLATFORM, {
  config: configSchema,
  lifecycle: {
    // Annotate the return type — this is what selects the fusor overload.
    createClient: async ({ config, projectConfig }): Promise&lt;FusorClient&lt;MyPayload&gt;&gt; =&gt; {
      if (projectConfig?.slug) await ensureWebhook(config, projectConfig.slug);
      return fusor&lt;MyPayload&gt;(MY_PLATFORM, verify(config));
    },
  },
  user:  { resolve: resolveUser },                      // ({ input }) =&gt; ({ id: input.userID })
  space: { create: createSpace },
  actions: { getDisplayName: async ({ config }, space) =&gt; /* … */ },
  messages: handleMessages,                             // typed `FusorMessages&lt;MyPayload, MyConfig&gt;` reference
  send,
});
```

Gotchas worth flagging to whoever writes the new channel:
- `messages` **must** be a typed non-inline reference or TS silently commits to the regular (async-iterable) overload — `define.ts:314-337`.
- Platform id must match `/^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$/`; `definePlatform` throws otherwise (`define.ts:38`), and duplicate names are rejected (`packages/core/src/platform/unique-names.ts`).
- `send` returns a `ProviderMessageRecord` for anything that produces a message (**including reactions** — synthesize a deterministic id if the API assigns none) and `undefined` only for fire-and-forget control signals.
- Never interpolate secrets into thrown errors or spans; use `tracedFetch(name, { redactUrl })` (see `redactBotToken`, `packages/telegram/src/client.ts:18`).</result>
